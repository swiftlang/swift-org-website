The Swift project once again participated in [Google Summer of Code](https://summerofcode.withgoogle.com) in 2026, helping newcomers to the open source ecosystem dip their toes into contributing to Swift and its growing ecosystem.

We also just introduced a new landing page for Swift's past (and future) GSoC participation, so feel free to check out [previous years' projects](https://www.swift.org/community/gsoc/) as well!

This year, we ran three projects, all of which were completed successfully:

* DocC language features in SourceKit-LSP
* Task and TaskGroup tracking for Swift Concurrency
* Qualified name lookup for swift-syntax

Here's a short summary of each project, with links to the full writeups to learn more.

### DocC Language Features in SourceKit-LSP

* Mentee: [Padmashree S S](https://github.com/Padmashree06)
* Mentors: [Matthew Bastien](https://github.com/matthewbastien), [Prajwal Nadig](https://github.com/snprajwal)
* Project writeup: [\[GSoC 2026\] DocC Language Features in SourceKit-LSP](https://forums.swift.org/t/gsoc-2026-docc-language-features-in-sourcekit-lsp/89281)

DocC is Swift's documentation compiler. It turns the doc comments in your code, along with Markdown articles and tutorials, 
into browsable documentation. Inside those comments and files, a symbol link points to a type, function, or property in your code, 
so readers can jump straight to it:

```swift
/// A type that greets people by name.
///
/// Call ``greet(_:)`` to produce a greeting, or use
/// ``Greeter/defaultName`` when no name is available.
struct Greeter {
    static let defaultName = "World"

    func greet(_ name: String) -> String {
        "Hello, \(name)!"
    }
}
```

Previously, a mistyped or broken symbol link wasn't caught until the whole documentation was built.

Padmashree extended SourceKit-LSP, Swift's language server, to understand DocC, so editors can check documentation as it's being written:

- Go to definition for symbol links in doc comments, Markdown, and Tutorial files
- Diagnostics for broken or invalid symbol links
- Clickable symbol links in the DocC preview that jump to the definition in your editor
- Syntax highlighting for DocC Markdown and Tutorial files

Because these features were implemented in SourceKit-LSP, they aren't limited to a single editor. They work in any editor that supports the Language Server Protocol (LSP) such as VS Code, Vim or others.

### Task and TaskGroup Tracking for Swift Concurrency

* Mentee: [Ege Kaya](https://github.com/egekaya1)
* Mentors: [Alastair Houghton](https://github.com/al45tair), [Mike Ash](https://github.com/mikeash)
* Project writeup: [\[GSoC 2026\] Task and TaskGroup tracking for Swift Concurrency](https://forums.swift.org/t/gsoc-2026-task-and-taskgroup-tracking-for-swift-concurrency/89084)

Programs in Swift use tasks to execute multiple things concurrently. Those tasks may be in different states, like actively running, sleeping, or waiting on another task to complete. 

Previously the Swift runtime did not have a registry of active tasks that was possible to query a process for, and e.g. use it to detect "stuck" tasks, which made diagnosing such resource leaks difficult.

Ege's project focused on implementing a high-performance always-on registry that will be enabled in Swift 6.5 that allows the concurrency runtime to track tasks in a process.

Debuggers like `lldb` and other tools, including `swift-inspect` can read this registry and offer developers valuable insights about the activity of tasks in their process. 

Since every task creation and teardown touches the registry, the design focused on minimal performance impact to existing code. 
Following mechanical sympathy techniques, the registry is split into 64 independent lists, or shards, avoiding false sharing when different processes record task creation/destruction in it.

In a stress test modeled on a web server that spawned over 600,000 tasks in a short burst, tracking them added about 0.015 seconds to a 0.37-second run; you can read more detailed analysis in the writeup above.

### Qualified Name Lookup for swift-syntax

* Mentee: [Filip Sakel](https://github.com/filip-sakel)
* Mentor: [Pavel Yaskevich](https://github.com/xedin)
* Project writeup: [\[GSoC 2026\] Qualified Name Lookup for swift-syntax](https://forums.swift.org/t/gsoc-2026-qualified-name-lookup-for-swift-syntax/89331)

Swift macros, linters, and code generators built on swift-syntax can read the structure of Swift code, but they couldn't easily perform contextual lookups.

For tool developers, getting those answers meant relying on libraries outside swift-syntax, or hand-rolling lookup themselves, which is a difficult task to get right.

Filip added qualified name lookup to swift-syntax's `SwiftLexicalLookup` module. It builds on the [GSoC 2024](/gsoc2024/#lexical-scopes-for-swift-syntax) project that introduced lexical scopes and unqualified name lookup, which already powers features in swift-java. Qualified lookup can be tricky to get right, as the example below illustrates: 

```swift
struct MyView { // <- In `struct MyView {}`, find members named 'model'
  #if true
  var model: Model // <- In type 'Model', find members named 'sayHi()'
  #endif
}
extension MyView {
  typealias Model = MyModel
}
final class MyModel {
  func sayHi() { print("Hi") }
}
```

In this example, we need to process extensions of the type `MyView` in order to discover that the `Model` type spelled inside `MyView`
actually refers to the `MyModel` class, through the `typealias Model` defined in the extension below the MyView definition. Implementing
these kinds of lookups manually is very difficult, and we're excited to have this functionality built into swift-syntax now!
